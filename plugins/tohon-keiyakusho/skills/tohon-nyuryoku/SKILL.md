# 謄本から契約書ひな型への自動転記

登記簿謄本を読み取り、契約書ひな型の「基本入力」シートへ書き込む。
基本入力は他の20シートから895か所参照されているため、ここが埋まれば重説・売契・媒介・約定まで自動で展開される。

処理は2段階。

1. **謄本PDFを読んで中間JSONを作る**(Claude自身が読む。ここが精度を左右する)
2. **中間JSONをひな型に書き込む**(`scripts/fill_tohon.py` が機械的に処理)

この2段階を分けているのは、謄本の書式が法改正等で変わっても、ひな型を改訂しても、中間JSONが変わらなければ片側だけ直せば済むようにするため。勝手に1段階にまとめないこと。

## 全体の流れ

### 重要事項調査報告書を受け取った場合

謄本とは独立した `scripts/important_report_store.py import PDF --unit-id 既存住戸UUID` を使用する。
標準JSON・原文根拠・項目別基準日を保存し、同一PDFの解析キャッシュを再利用する。
対応住戸が不明ならunit-idを推測せず、未照合の要確認資料として保存する。物件を新規作成しない。
重調を謄本用JSONへ変換したり、`fill_tohon.py` へ渡したりしない。
確定版であっても自動承認しない。利用者が原本確認して採用すると明示した項目だけ、
`approve 資料版UUID --fields 標準field_code --reviewed-by 確認者` で承認する。
画像・根拠不一致の値は原本との照合後に限り `--verified-against-original` を使用する。
承認後は `export 資料版UUID ひな形.xlsm -o 出力.xlsm` で反映する。
名前定義がない項目を固定セルへ書かない。現行正式ひな形では物件名・号室の2項目が対応する。
それ以外はDB保存＋要確認表示まで。承認済みでも低confidence・根拠不明・needs_review=trueの値は転記しない。詳細はリポジトリの `IMPORTANT_REPORT_ADMIN.md`。

### 謄本の場合（既存処理）

1. 謄本PDFの場所と、契約書ひな型の場所を確認する
2. `references/reading-rules.md`(謄本読み取りルール) を**必ず読む**
3. 物件の類型を判定する(戸建てなら対象外として止まる)。謄本PDFを読んで中間JSONを作る
4. `scripts/store_and_fill.py` でSupabaseへ保存し、成功した場合だけ既存 `scripts/fill_tohon.py` を実行する
5. 書き込み結果と要確認事項を報告する

## 対象外の物件

**戸建ては対象外。** 謄本の表題部が「主である建物の表示」になっていたら戸建て。
このひな型は区分所有が前提の作りのため、無理に当てはめない。

その場合は転記を行わず、「戸建ては対象外です」とユーザーに伝えて止まる。
どうしても進めたいと言われたら、どの欄に何を入れるか運用ルールを確認してから作業する。
勝手に一棟／専有の欄へ割り当てない。

## ステップ1: 対象の確認

- 謄本PDFの場所が分からなければ聞く。Cowork上でフォルダアクセスが必要なら `mcp__cowork__request_cowork_directory` でリクエストする
- 契約書ひな型(.xlsm)の場所も確認する。原本は書き換えず、必ずコピーを出力する(スクリプトがそうしている)
- **名前定義版のひな型でなければ動かない。** 古いひな型を渡されるとスクリプトが門前払いするので、
  その場合は最新のひな型の場所をユーザーに確認する
- フォルダを渡された場合は中身を確認し、**建物の全部事項証明書**を主データとして使う
- 土地の全部事項証明書は、非敷地権マンションと借地物件では**必須**(持分・地代・貸主がそこにしか無い)。それ以外では突合用
- テキスト層の無いスキャンPDFは画像として読む。`pdftoppm -r 200 -png` で画像化してから読めば問題なく読み取れる
- 複数物件が入っていたら、物件ごとに1件ずつ処理する。勝手に1ファイルにまとめない

## ステップ2: 読み取りルールを読む

`references/reading-rules.md`(謄本読み取りルール) を読むこと。**このステップを飛ばさない。**

謄本には、読み飛ばすと契約書が丸ごと間違う罠がいくつもある(下線＝抹消事項、氏名が1字ずつ空いている、最新でない所有者を拾ってしまう、地下階の見落とし等)。ルールファイルにその全てが書いてある。

## ステップ3: 中間JSONを作る

読み取りルールに従って、謄本から情報を抽出しJSONファイルとして保存する。

- **謄本に書かれていない項目は推測で埋めない。** 空文字か null にする
- 自信が持てない項目、契約実務上ひっかかる点は `_要確認` 配列に日本語で書く
- ファイル名は物件が分かる名前にする(例: `◯◯マンション704.json`)

## ステップ4: 書き込みの実行

```bash
python3 scripts/store_and_fill.py <中間JSON> <ひな型.xlsm> -o <出力.xlsm> --source <原本PDF> --house-number <原文確認済みの完全な家屋番号>
```

- 出力先は、ユーザーが指定しなければ謄本と同じフォルダに `<物件名>_記入済み.xlsm` として置く
- スクリプトが「書き込み」「スキップ」「要確認」を一覧で出力する。これを必ず読む
- `要確認` に**住居表示が謄本の所在と違う**旨が出たら、そのまま渡さずユーザーに伝える。所在は住居表示から組み立てられるため、ここが違うと全シートの所在が間違う
- `スキップ` が出た場合は理由を確認する。数式セルを守った結果なら正常

スクリプトは以下を自動で守る。壊れた出力を渡さないための仕掛けなので、これを迂回して openpyxl で直接書き込むようなことはしない。

- 数式セルには書き込まない
- 結合セルは左上のアンカーにのみ書き込む
- マクロ(VBA)を保持する
- 書き込み後に数式の総数を数え、減っていたら警告する

Supabase接続には環境変数 SUPABASE_URL と SUPABASE_SERVICE_ROLE_KEY を使う。保存失敗時はExcel作成を停止し、日本語のエラーを報告する。保存を迂回して fill_tohon.py を直接呼ばない。中間JSONの日本語キーと読み取りルールは変更しない。完全な家屋番号は既存JSONに末尾しかないため、原文で確認した全文を呼出引数へ渡す。建物名・構造化済み抵当権・根拠等を補足する場合はDB専用の --db-context を使い、中間JSONへキーを追加しない。

## ステップ5: 報告

ユーザーには次を伝える。

1. 出力ファイルの場所
2. 転記した主要項目(所在・家屋番号・専有面積・延床面積・地積・持分・所有者・建築時期)
3. `_要確認` と、スクリプトが出した警告の全て
4. **謄本と並べて目視確認するよう促す**。自動転記の結果をそのまま契約書として使わせない

## 謄本からは埋まらない項目

以下は謄本に情報が無い。埋まっていなくても異常ではないので、そう伝える。

- 買主、物件名、住居表示、間取り、壁芯面積
- 契約日、物件価格、手付金、消費税、仲介手数料
- 融資関係(金融機関・金額・金利・期間・承認取得期日)
- 業者情報、宅建士情報

なお**住居表示は謄本より先に入力が必要**。ひな型は所在・家屋番号・土地1筆目の所在をここから組み立てるため。

## 複数物件をまとめて処理するとき

1件ずつ、ステップ2〜4を繰り返す。最後にまとめて報告する。

- 途中で1件失敗しても残りを続ける。最後に失敗した物件を明示する
- 件数が多くても、最初の承認後は1件ごとに確認を求めない
- ただし `要確認` が出た物件は、件数に関わらず全て報告に含める

## ひな型を改訂したとき

書き込み先は `scripts/mapping.json` の対応表で決まる。対応表はひな型の**名前定義**を参照している
(`謄本_所有者_氏名` など)。Excelで行を挿入・削除しても名前定義が追従するため、
**通常は対応表もスクリプトも直さなくてよい。**

入力欄そのものを新設・移動したときだけ、Excelの「数式」→「名前の管理」で名前の参照先を直す。
`fill_tohon.py` は触らない。

対応表に名前ではなくセル番地(`AB24` など)が書かれていると、スクリプトは動くが警告を出す。
その項目にはまだ名前定義が無いということなので、ひな型側に名前を付ける。
